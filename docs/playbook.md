# Quality Assurance Kit — Playbook

This playbook defines the end-to-end process for the Quality Assurance Kit (Layer 9). It covers how to move from a frozen Operational Readiness Document to a quality disposition that either clears the initiative for release or returns it to engineering.

---

## Artifact Flow

```
Upstream: Frozen ORD from Engineering Execution Kit (Layer 4)
         + SAD (integration points) + TDD (test strategy) + ACF (constraints) + WDD (traceability)
         │
         ▼
Step 0: Quality Assurance Entry Record (QAER) — human-authored
         │ Validate → Freeze
         ▼
Step 1: Verification Plan (VP) — generated
         │ Validate → Freeze
         ▼
Step 2: Test Campaign Record (TCR) — generated from execution evidence
         │ Validate → Freeze
         │ (one or more TCRs per VP; each covers a test campaign)
         ▼
Step 3: Quality Gate Record (QGR) — generated from TCR(s) + VP + defect status
         │ Validate → Freeze
         ▼
Handoff to Layer 5 (Release & Exposure Kit)
```

Steps 2 may repeat if the verification plan is executed in multiple campaigns (e.g., separate integration, performance, and security campaigns). All TCRs must be frozen before the QGR is generated.

---

## Upstream Interface

**Upstream:** Engineering Execution Kit (Layer 4)
**Input:** Frozen ORD, plus the following EEK artifacts for reference:

| Artifact | What QAK Uses It For |
|----------|---------------------|
| ORD (frozen) | Confirms operational readiness; gates QAK entry |
| SAD (System Architecture Document) | Integration points that require cross-component verification |
| TDD (Technical Design Document) | Test strategy and unit test coverage baseline |
| ACF (Architecture Context File) | Constraints that tests must verify (performance, security, compliance) |
| WDD (Work Decomposition Document) | Work items for traceability from requirements to tests |

If the ORD is not frozen, do not begin the entry gate. Request a frozen ORD from the upstream engineering team.

---

## Step 0 — Quality Assurance Entry Gate

**Artifact:** Quality Assurance Entry Record (QAER)
**Type:** Human-authored entry gate
**Spec:** `docs/specs/qaer-spec.md` (5 hard gates)
**Template:** `docs/artifacts/qaer-template.md`
**Validator:** `docs/validators/qaer-validator.md`

### Purpose

The QAER confirms the upstream handoff is complete, identifies the QA owner, confirms test infrastructure readiness, and identifies integration points from the SAD that require cross-component verification. It is not generated by AI — the QA owner completes it.

### Inputs
- Frozen ORD from the Engineering Execution Kit
- SAD (for integration point identification)
- TDD (for test strategy baseline)

### Process

1. The QA owner obtains the frozen ORD and supporting EEK artifacts (SAD, TDD, ACF, WDD).
2. Using the QAER template, the owner completes all sections: upstream reference (capturing ORD status), QA owner contact, test infrastructure confirmation, and integration point identification from the SAD.
3. The owner verifies that test infrastructure (environments, test data, tooling) is ready for the verification scope.
4. The owner identifies all integration points from the SAD that require cross-component verification and documents them.
5. The completed QAER is validated in a separate session from the one that completed it.
6. On PASS: the QA owner reviews and freezes the QAER. **No VP generation may begin until the QAER is Frozen.**
7. On FAIL: address blocking issues and re-validate.

### Freeze Points
- QAER must be Frozen before VP generation begins

---

## Step 1 — Verification Plan

**Artifact:** Verification Plan (VP)
**Type:** Generated
**Spec:** `docs/specs/vp-spec.md` (4 hard gates)
**Template:** `docs/artifacts/vp-template.md`
**Prompt:** `docs/prompts/vp-prompt.md`
**Validator:** `docs/validators/vp-validator.md`

### Purpose

The VP defines what to test beyond unit tests: integration tests, system tests, performance tests, and security tests. It establishes measurable pass/fail criteria for each test category and maps tests to requirements for traceability.

### Inputs
- Frozen QAER
- SAD (integration points, component boundaries)
- TDD (test strategy, unit test coverage baseline)
- ACF (performance, security, and compliance constraints)
- WDD (work items for traceability)
- Frozen TM from SCK (optional — if adopted, provides threat model for security test scope)
- Frozen SAR from SCK (optional — if adopted, provides security assessment findings to verify)

### Process

1. In a new AI session, provide: frozen QAER + SAD + TDD + ACF + WDD + `docs/specs/vp-spec.md` + `docs/artifacts/vp-template.md`. Use the VP prompt (`docs/prompts/vp-prompt.md`).
2. Review the generated VP. Check that all SAD integration points are addressed, acceptance criteria are measurable, and test environments are specified.
3. Validate the VP in a separate session using `docs/validators/vp-validator.md` and the spec.
4. On PASS: human review and freeze. **The frozen VP is now the authoritative test scope.**
5. On FAIL: address blocking issues and re-generate or correct; re-validate.

### Freeze Points
- VP must be Frozen before TCR generation begins
- Frozen VP is immutable; changes require re-entry protocol

---

## Step 2 — Test Campaign Record

**Artifact:** Test Campaign Record (TCR)
**Type:** Generated (from execution evidence)
**Spec:** `docs/specs/tcr-spec.md` (4 hard gates)
**Template:** `docs/artifacts/tcr-template.md`
**Prompt:** `docs/prompts/tcr-prompt.md`
**Validator:** `docs/validators/tcr-validator.md`

### Purpose

The TCR documents the execution of the verification plan: test results, environment used, defects found, and coverage achieved. It is an evidence artifact — it captures what was tested and what the results were.

### Inputs
- Frozen VP (the plan being executed)
- Test execution evidence: test results, logs, screenshots, metrics
- Environment details: configuration, versions, test data used
- Defect records: defects found during testing with severity and status

### Process

1. Execute the tests defined in the frozen VP. Collect all evidence: test results, environment details, defect records.
2. In a new AI session, provide: execution evidence + frozen VP + `docs/specs/tcr-spec.md` + `docs/artifacts/tcr-template.md`. Use the TCR prompt (`docs/prompts/tcr-prompt.md`).
3. Review the generated TCR. Confirm test results match the evidence, all VP tests are accounted for, and defects are accurately recorded.
4. Validate in a separate session using `docs/validators/tcr-validator.md` and the spec.
5. On PASS: QA owner reviews and freezes. **The TCR is now an immutable evidence record.**
6. On FAIL: address blocking issues and re-validate.

### Multiple TCRs

If the VP is executed in multiple campaigns (e.g., integration tests in one campaign, performance tests in another), each campaign produces its own TCR. All TCRs must reference the same frozen VP and collectively cover the full VP scope.

### Freeze Points
- All TCRs must be Frozen before QGR generation begins
- A frozen TCR is not amended; corrections require a new TCR version

---

## Step 3 — Quality Gate Record

**Artifact:** Quality Gate Record (QGR)
**Type:** Generated
**Spec:** `docs/specs/qgr-spec.md` (5 hard gates)
**Template:** `docs/artifacts/qgr-template.md`
**Prompt:** `docs/prompts/qgr-prompt.md`
**Validator:** `docs/validators/qgr-validator.md`

### Purpose

The QGR is the terminal artifact. It aggregates TCR results, coverage data, and defect status to declare a quality disposition: PASS (proceed to REK), CONDITIONAL (proceed with noted risks), or FAIL (return to EEK).

### Inputs
- All frozen TCRs for this initiative
- Frozen VP (for coverage assessment)
- Defect status summary (all defects with current status)
- Risk assessment context

### Process

1. Collect all frozen TCRs, the frozen VP, and current defect status.
2. In a new AI session, provide: all TCRs + VP + defect status + `docs/specs/qgr-spec.md` + `docs/artifacts/qgr-template.md`. Use the QGR prompt (`docs/prompts/qgr-prompt.md`).
3. Review the generated QGR. Confirm the disposition is justified by evidence, all critical/high defects are accounted for, and residual risks are documented.
4. Validate in a separate session using `docs/validators/qgr-validator.md` and the spec.
5. On PASS: QA owner and project lead review and freeze.
6. On FAIL: address blocking issues; re-generate or correct; re-validate.

### Disposition Values

| Disposition | Meaning | What Happens Next |
|-------------|---------|-------------------|
| PASS | All quality criteria met; no blocking defects | Proceed to REK (Layer 5) |
| CONDITIONAL | Quality criteria mostly met; accepted residual risks documented | Proceed to REK with conditions noted in QGR §Conditions |
| FAIL | Quality criteria not met; blocking defects or coverage gaps exist | Return to EEK for remediation; re-enter QAK after fixes |

### Freeze Points
- QGR must be Frozen before handoff to REK
- A frozen QGR is the quality clearance for release entry

---

## Downstream Handoff

**Downstream:** Layer 5 (Release & Exposure Kit)
**Handoff artifact:** Frozen QGR — specifically §Quality Disposition

The Quality Disposition provides:
- Disposition: PASS, CONDITIONAL, or FAIL
- Evidence summary referencing TCR IDs
- Residual risks (if CONDITIONAL)
- Conditions for proceeding (if CONDITIONAL)
- Blocking issues (if FAIL)

Layer 5 requires a frozen QGR with PASS or CONDITIONAL disposition before release entry. A FAIL disposition blocks release entry.

## Freeze Points Summary

| Artifact | When Frozen | What It Gates |
|----------|------------|---------------|
| QAER | Before VP generation | VP generation |
| VP | After validation | TCR generation |
| TCR | After validation | QGR generation (all TCRs must be frozen) |
| QGR | After validation | REK entry (Layer 5 handoff) |

## Session Discipline

Follow these rules in every AI session:

| Rule | Why |
|------|-----|
| One artifact per session | Prevents context contamination across artifacts |
| Separate generation and validation sessions | Prevents self-validation bias |
| Include full frozen upstream artifacts | Do not summarize; the AI needs complete context |
| Include spec and template for generation sessions | The AI generates against the spec, not from memory |
| Include spec and validator for validation sessions | The validator judges against the spec, not against the generated content |

Do not ask the AI that generated an artifact to also validate it in the same session.

---

## Re-Entry Protocol

When a frozen artifact must be corrected:

1. Identify the artifact to be changed (QAER, VP, TCR, or QGR).
2. Identify all downstream artifacts that reference it or depend on it.
3. Assess the impact: does the change affect test scope, results, or disposition?
4. Issue a new version of the artifact (e.g., VP v2, TCR-PROJECT-001v2).
5. Re-validate the new version.
6. Re-validate all affected downstream artifacts that reference the changed artifact.
7. Document the change in the new version's document control section with a reference to the original and the reason for the correction.

---

## Abort Protocol

If the entry gate (QAER) reveals that the ORD is not frozen or EEK artifacts are incomplete:

1. Do not proceed with VP generation.
2. Document the gap in the QAER as a blocking issue.
3. Contact the upstream engineering team and request completion of the missing artifacts.
4. Hold QAK intake at the QAER step until the gap is resolved.

If test execution reveals that the VP scope cannot be fully executed (e.g., environment unavailable):

1. Document the gap in the TCR with specific tests not executed and the reason.
2. The QGR must account for unexecuted tests in its coverage assessment and risk analysis.
3. A PASS disposition is not possible if required tests were not executed without documented justification.

---

## Amendment Procedure

A frozen artifact may be corrected in place without re-validation when **all** of the following criteria are met:

1. The correction does not affect any field evaluated by a hard gate.
2. The correction does not change scope, decisions, owners, or technical specifications.
3. The correction does not affect any field referenced by a downstream artifact.

**Procedure:** Make the correction and add an Amendment Log entry to the artifact's Document Control section: date, what changed, materiality criterion cited, and who authorized the change. No re-validation is required.

**If there is any ambiguity** about whether a change is non-material, treat it as material and issue a new artifact version. The amendment path must not become a workaround for the version protocol.

---

## FAIL Disposition Re-Entry

When a QGR has a FAIL disposition:

1. The QGR documents the blocking issues and returns the initiative to EEK.
2. The engineering team addresses the blocking issues (defect fixes, coverage gaps).
3. After fixes are complete and the ORD is re-validated, the initiative re-enters QAK.
4. A new QAER is completed referencing the updated ORD.
5. The VP may be reused if the scope has not changed; otherwise, generate a new VP.
6. New TCRs are generated for the re-test campaign.
7. A new QGR is generated from the new TCRs.

## Maintaining the Engagement Record

The Engagement Record (ER) is a project-level artifact that lives in the consuming project at `docs/engagement/er-{initiative}.md`. It spans all AIEOS layers and is maintained by each kit's operators as work passes through. The ER spec and format are defined in `aieos-governance-foundation/docs/engagement-record-spec.md`.

**QAK maintains the Layer 9 section of the ER.**

### What to Update During QA Operations

| Trigger | ER update |
|---------|-----------|
| QAER frozen | Add QAER ID to artifact table |
| VP frozen | Add VP ID to artifact table |
| TCR frozen | Add TCR ID to artifact table |
| QGR frozen | Add QGR ID to artifact table; record disposition in Notes column |
| QGR FAIL | Note FAIL disposition and re-entry plan |
| QGR CONDITIONAL | Note CONDITIONAL disposition and accepted conditions |
